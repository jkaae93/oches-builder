# ARC-11 신뢰 UI·키 보호·상호 인증 선택지와 검증

상태: 설계 비교 및 격리된 기초 실험 · 2026-11-16. 제품 Core, 서명된 제품 앱, 실제 등록·승인 프로토콜과 OS 키 보호는 구현하거나 실험하지 않았다. G3는 UNKNOWN이다. 어떤 선택지도 공식 문서만으로 제품 안전성을 보장하지 않는다.

## 먼저 입증해야 할 경계

1. **등록 최초 신뢰:** 사용자가 확인하는 등록 UI와 Core가 실제 제품 구성요소인지, 표시된 클라이언트·workspace·권한이 실제 등록 결과와 같은지 입증한다. 악성 앱이 먼저 자신을 Core나 UI로 등록하면 이후 올바른 서명 교환만으로 복구되지 않는다.
2. **연결 상대 신원:** 각 IPC 연결의 양쪽에서 실행 중인 peer를 안전하게 식별하고 검증된 신원을 그 연결에 결부한다. 파일 경로·PID·동일 UID·Extension ID·Origin만으로 충분하지 않다. PID 재사용과 검사/사용 사이 교체를 포함해 대상 OS의 공식적으로 지원되는 증거를 확인한다.
3. **개인키 보호와 사용 제한:** 단순한 비밀 보관뿐 아니라 신뢰되지 않은 같은 사용자 프로세스가 키를 내보내거나 정당한 구성요소를 서명 대리자로 악용할 수 없는지 확인한다. 키 소유는 등록된 앱의 무결성이나 사용자의 행위별 의도를 자동 증명하지 않는다.
4. **상호 인증과 재생 방지:** 양쪽 신원, 프로토콜 버전, 연결 및 등록 상태와 관련된 유효기간 내의 새로운 challenge를 검증하고, 사용한 challenge의 중복을 원자적으로 거부한다. 서명할 표현의 정규화·domain separation 및 정확한 채널 바인딩은 ARC-11의 후속 계약이다. 구현 전 실효성을 주장하지 않는다.
5. **권한과 승인:** 인증 뒤에도 workspace·작업·대상·권한·revision·유효 기간을 독립 검사한다. 확인 UI가 검증 가능한 내용에 대해 승인하지 않았거나, 철회·변경·저장 실패가 발생하면 실행을 차단한다.

## 선택지 비교

| 선택지 | 가능한 장점 | 외부 전제·주요 위험 | 채택 전 최소 검증 및 실패 시 |
|---|---|---|---|
| 서명된 전용 Core/신뢰 UI + OS 보호 키 + 양방향 인증 | 코드 신원과 키 사용을 각 구성요소에 묶을 가능성 | 배포 서명·팀/식별자·entitlement·업데이트 체계와 OS의 live peer 판별이 필요하다. 서명된 앱 자체가 악성 입력에 서명해 주는 대리자가 될 수 있다 | 동일 사용자 위장 프로세스·앱 복사/교체·가짜 Core·재생·승인 위조·키 사용 우회 부정 대조와 정상 제품 양성 대조. 어느 경계라도 미확인 시 변경·실행 차단 |

| 제품이 없는 현재 단계에서 위험 기능 미지원 | 검증되지 않은 신뢰를 부여하지 않는다 | 실제 연결 UX·업데이트·성능은 알 수 없으며 사용자에게 동작을 제공할 수 없다 | 선행 증거가 없는 플랫폼·클라이언트는 설치·연결 상태를 unknown으로 표시하고 변경/실행은 차단 |

Desktop·VS Code·Chrome을 동일 주체로 간주하지 않는다. VS Code `SecretStorage`나 Chrome Native Messaging 허용 Extension 목록은 각각의 공식 플랫폼 기능일 뿐, Oches의 live Core 신원·브로커 권한·정당한 사용자 확인을 자동 보증하지 않는다. OS 저장소나 Secure Enclave는 키를 보호하는 후보이며 접근 권한을 가진 프로세스의 오용, 신뢰 UI 위장 및 초기 등록 문제를 독립적으로 검증해야 한다.

## 격리 실험과 관찰

### 정적 서명 식별자 부정 대조

[macOS 코드 신원 실험](MACOS_IDENTITY_EXPERIMENT.md)의 [재현 스크립트](experiments/verify-macos-adhoc-identity.py)는 다른 두 임시 실행 파일을 같은 ad-hoc 식별자로 서명한다. macOS 26.4 arm64에서 두 파일은 모두 무결성 검사와 identifier-only 조건을 통과했고, Apple generic anchor 추가 시 ad-hoc 부정 대조는 거부됐으며 파일 바이트 변조 후 무결성 검사도 실패했다. Developer ID 양성 대조·live peer 검사는 NOT RUN이므로 Apple anchor가 제품 인증 해법으로 검증됐다는 뜻이 아니다.

### 키 소유 증명 부정 대조

[임시 키 실험 스크립트](experiments/verify-key-possession-boundaries.py)를 macOS 26.4, LibreSSL 3.3.6에서 실행했다. 임시 디렉터리의 두 P-256 키 중 맞는 공개키는 서명을 검증했고, 다른 공개키와 변경된 메시지는 거부됐다. **같은 서명과 메시지를 다시 제출하면 암호 검증은 다시 성공**했다. 즉 서명 검증만으로 재생 방지는 되지 않는다. 같은 OS 사용자로 실행한 별도 OpenSSL 프로세스가 임시 `0600` 키 파일을 사용해 서명했으므로 파일 모드만으로 같은 사용자 내 앱 격리를 제공하지 않는다. 임시 키·출력은 삭제했으며 사용자 Keychain·Secure Enclave·실제 인증은 사용하지 않았다.

이 실험은 키 사용과 단순 재생의 암호학적 동작에 한정된다. 실제 랜덤 nonce, 소비 기록의 원자성·만료·재시작 처리, 메시지 순서, 네트워크/IPC 채널 바인딩, 신뢰 UI와 OS 키 보호를 구현·검증하지 않았다. 서명에 포함된 `core-A` 문자열도 실제 Core 신원을 증명하지 않는다.

## 실험 게이트와 결과 기록

후속 시험은 서명된 격리용 테스트 구성요소와 별도 승인된 환경을 사용한다. 비밀·토큰 없이 OS/버전, 빌드·서명 유형, 입력/관찰·기대 판정·정책 버전·증거 경로·판정자·PASS/FAIL/NOT RUN을 기록한다. **서명된 정상 앱 양성 대조가 없는 부정 대조만으로 PASS를 선언하지 않는다.**

| ID | 양성 / 부정 대조 | 필수 기대 결과 |
|---|---|---|
| SEC-01 | 신뢰된 테스트 앱 / 같은 identifier의 ad-hoc 또는 다른 발행자 | 양성 수락, 부정 거부. 연결 peer와 검증 대상의 결부도 확인 |
| SEC-02 | 정당한 Core / 소켓 선점·가짜 Core·키 교체 | 정당한 Core 수락, 최초 등록 및 재연결에서 가짜 Core 거부 |
| SEC-03 | 정당한 구성요소의 키 사용 / 같은 사용자 다른 프로세스의 내보내기·서명 대리 요청 | 허용 범위만 성공. 접근 제한과 키 비추출성 미확인 시 차단 |
| SEC-04 | 새로운 challenge / 재생·만료·다른 대상·동시 중복 응답 | 첫 유효 요청만 수락, 나머지 거부. 소비 기록 및 장애·재시작을 검증 |
| SEC-05 | 권한·revision이 일치한 신뢰 UI 승인 / 위조 UI·재전송·권한 철회·변경된 대상 | 지정 범위만 허용. 승인 자체로 앱 신원을 대체하지 않음 |
| SEC-06 | 등록된 확장·Helper / 허용되지 않은 확장·페이지·Host 교체 | 사용자 데이터·Core 변경 및 실행 요청이 부정 대조에서 거부됨 |

[Apple Secure Enclave 문서](https://developer.apple.com/documentation/security/protecting-keys-with-the-secure-enclave)는 보호된 키 사용의 조건을 설명하고, [Apple 키 내보내기 문서](https://developer.apple.com/documentation/security/storing-keys-as-data)는 일부 키의 비내보내기 조건을 설명한다. 이는 Oches의 특정 배포 구성에서 격리가 확인됐다는 의미가 아니다. [NIST SP 800-63B](https://pages.nist.gov/800-63-4/sp800-63b.html)는 challenge의 신선성과 재생 저항을 설명한다. Oches 프로토콜은 아직 구현되지 않았으므로 이 자료에 대한 적합성을 주장하지 않는다.

## 현재 결론

macOS의 정적 코드 서명과 임시 파일 키 실험은 두 가지 취약한 단독 판단을 배제하는 근거다. **신뢰 UI, 키 보호, 양방향 인증의 실효성은 아직 UNKNOWN**이다. 사용자 Keychain, 실제 Provider 인증과 유료 모델 호출은 사용하지 않았다. Windows/Linux 및 실제 제품 실험도 NOT RUN이다. 독립 리뷰 점수 75~76이나 G3를 올리지 않는다.

### 후속 설계 점수 평가

위 75~76점 언급은 이 신뢰 경계 비교를 작성할 당시의 중간 평가다. 이후 예외·의존성에 대한 보안 및 비용 독립 리뷰를 종합한 설계 점수는 [REVIEW_80](REVIEW_80.md)을 따른다. G3 UNKNOWN과 이 문서의 미실행 조건은 변하지 않는다.

## 플랫폼 식별 보충

Chrome의 `allowed_origins`와 Chrome 전달 caller origin은 정상 플랫폼 경로에서 실질적인 확장 접근 제한·식별이다. VS Code `publisher.name`은 공식 설치·관리 식별자다. 직접 Host 실행 또는 공유 Host에서 Core까지 신원 결부가 제공되는지는 별도 문제다. 구체 흐름과 검증은 [확장 신원 경계](EXTENSION_IDENTITY_BOUNDARIES.md)를 따른다.
