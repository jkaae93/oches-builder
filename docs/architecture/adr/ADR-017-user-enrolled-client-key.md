# ADR-017: 사용자가 등록한 설치키의 제한적 신뢰

상태: **사용자 채택 — 설계 기준** · 2026-11-16. 사용자는 Chrome·VS Code 플랫폼 식별을 확인하고 사용자가 등록한 설치별 키와 Desktop의 요청별 승인을 신뢰하는 방식을 선택했다. [ADR-016 D03](ADR-016-core-contract-baseline.md)의 플랫폼→Core 개별 확장 신원 증명 필수 조건은 이 모델의 범위에서 변경한다. 플랫폼 식별과 키 보유, Desktop 승인은 구별하며 제품 지원이나 보안 시험 통과를 뜻하지 않는다.

## 결정 대상과 신뢰 모델

Core가 개별 확장의 OS 검증 신원을 확보하지 못하는 경로에서, 사용자가 확인한 **설치별 공개키**를 `enrolledClient` 주체로 삼는다. Chrome allowlist/origin 및 VS Code `publisher.name`·Workspace Trust는 가능한 플랫폼 접근 제한과 표시 정보로 계속 사용한다. Core는 그것들을 독립 증명된 확장 신원이라고 주장하지 않는다. 등록된 키가 실제 어떤 확장에서 생성됐는지 사용자의 확인 및 해당 환경의 무결성에 의존한다.

위협 모델은 비신뢰 웹페이지·workspace, 등록되지 않은 키의 직접 Host 호출, 저장된 proof 재생·수정, 권한 밖 요청을 포함한다. 사용자의 Desktop 승인 UI 위장, 같은 사용자 환경의 완전한 장악, 확장 실행 문맥의 악성 코드 또는 키를 사용하는 정상 확장의 실시간 서명 대리까지 이 선택지만으로 차단한다고 주장하지 않는다. [RFC 9449 §11.4](https://www.rfc-editor.org/rfc/rfc9449.html#section-11.4)는 클라이언트 실행 문맥을 장악한 코드가 비추출 키를 간접 사용할 수 있음을 설명한다.

## 등록과 호출

1. 사용자가 OS의 설치 출처와 Desktop UI를 확인한 후 확장을 열고 등록한다. [등록 transcript](../CLIENT_INSTALLATION_AUTH_DESIGN.md#최초-core-키-확인-및-noise-키-결부-계약)는 Core/확장 서명 공개키 및 Noise static 공개키, nonce, workspace, 권한을 RFC 8785 JCS로 정규화하여 두 화면에 결부하고 키 소유 증명·사용자 확인·감사 후 등록한다. 두 화면이 같은 코드를 표시해도 실시간 relay나 위장 UI가 배제된다는 주장은 하지 않는다. 안전한 Desktop↔Core peer, UI 및 확장 키 보호 조건이 불명이면 등록을 보류한다.
2. 등록 주체는 `user-enrolled-key`와 지문·사용자 지정 이름·생성/만료/철회·workspace 범위·정책 버전으로 기록한다. 플랫폼 ID는 `platform-asserted` 또는 `unverified` 같은 별도 증거 수준으로 표시하고 키의 소유자를 OS가 확증한 것처럼 표시하지 않는다. 등록은 `approval:decide` 권한을 주지 않는다.
3. 각 요청은 [서명·단회 nonce·재시도 계약](../CLIENT_INSTALLATION_AUTH_DESIGN.md#위험-요청의-종단-서명-및-noise-채널-결합-계약)을 따른다. Core는 등록키 서명·현재 등록/정책·workspace·요청 digest·nonce·기대 revision을 확인한다. 동일 requestId의 재조회와 새 실행은 구분한다. 키 보유만으로 읽기·실행·사용자 승인 권한을 부여하지 않는다.
4. Core의 신뢰 Desktop UI에서 사용자가 해당 행위·대상·workspace·입력 digest·작업/시도·만료를 직접 검토·승인한다. 설정 변경, 외부 실행과 데이터 전송은 각각 별도 승인이다. Extension/Webview/페이지는 UI를 통한 승인 결정을 발급할 수 없다. 수신자, 대상이나 입력이 바뀌면 승인은 무효다. UI와 Core의 신원 확인·내용 표시 무결성을 보장할 수 없으면 실행하지 않는다.
5. 원본 관찰, 비밀·민감 workspace 데이터 및 Provider 인증정보는 이 방식의 기본 권한에 포함하지 않는다. 서명은 기밀성을 제공하지 않으므로 검증된 종단 기밀성이 없으면 해당 내용 반환·전송을 차단한다. 취소 요청·연결 단절과 외부 프로세스의 실제 종료는 구분한다. 키 철회는 새 요청을 거부하고 실행 중 작업은 취소 요청 후 종료를 확인한다.

### 읽기·출력 범위와 기능 영향

`USER_ENROLLED_KEY`도 현재 등록·workspace·행위별 읽기 권한을 Core가 매 조회마다 재확인한다. 권한이 있더라도 검증된 종단 기밀성 없이 Host가 볼 수 있는 경로에는 프로젝트 경로·이름, Profile·파일/페이지 내용, task/attempt 식별자와 상태, 분석·평가 결과, 원본 로그·산출물, 승인 범위 및 거부의 민감 사유를 보내지 않는다. 필요한 경우 존재 여부를 감춘 범용 오류만 제공하고 빈 응답을 실제 데이터 부재로 표시하지 않는다. 시간·메시지 크기와 요청 빈도 같은 부수 정보는 범용 오류만으로 완전히 숨길 수 없으므로 관찰 가능성을 표시하고 위험 모델에서 검토한다.

| 제품 기능 | 이 대안에서 필요한 조건 | 조건 부재 시 |
|---|---|---|
| Chrome 페이지 선택 제출 | 사용자가 명시한 선택·출처·수신 범위, 해당 데이터 전송에 대한 사용자 승인과 종단 기밀성 | Core에 페이지 내용을 보내지 않고 불가 사유 표시 |
| VS Code workspace/Profile 표시 | 현재 workspace 읽기 인가와 종단 기밀성, 로컬/원격 위치 확인 | 경로·프로젝트·Profile을 노출하지 않고 지원 보류 표시 |
| 작업·이벤트 모니터링 | 각 작업의 현재 읽기 권한 및 종단 기밀성; 원본 로그는 추가 권한 | 범용 상태 외 세부 정보는 공개하지 않으며 결측을 명시 |
| 구성 수정·실행·외부 전송 | 등록키 서명·정책·대상/입력 결부 및 해당 작업의 Desktop 승인; 실행 환경의 강제 능력 | 요청을 승인 대기/거부로 표시하고 부작용 시작 금지 |

위 표의 조건은 기능을 영구 제외한다는 결정이 아니다. 확장–Core의 전송 암호화(`Noise_IK_25519_ChaChaPoly_SHA256`), 4 KiB 버킷 패딩, 일관된 범주형 외부 오류 매핑 및 수신자 인증 계약은 [종단 보안 채널 설계](../EXTENSION_SECURE_CHANNEL.md)와 [설치별 인증 설계](../CLIENT_INSTALLATION_AUTH_DESIGN.md)에 확정했다. 승인된 UI가 표시하는 정보도 중계자를 통해 받아 검증 없이 표시하지 않는다.

## 지원과 전환

Core의 인증 결과는 `USER_ENROLLED_KEY`와 `PLATFORM_BOUND`를 분리한다. 기존 `identityVerified=true`를 사용자 확인 키에 부여하지 않는다. [주체별 권한 계약](../CLIENT_INSTALLATION_AUTH_DESIGN.md#주체별-권한-및-사용자-표시-계약)과 ARC-11은 이 구분을 따른다. 기능별 사용 가능성은 사용자가 등록한 키·검증된 Desktop UI·요청별 승인·데이터 보호의 조건에 한정해 표기한다. 설계 계약(G3 설계 기준)은 확정되었으나, Remote Host·Windows/Linux·Chrome/VS Code별 실제 OS 배포 및 제품 보안 시험은 **NOT RUN**이다.

양성 대조는 등록된 두 키 각각의 정상 요청과 명시적 Desktop 승인이다. 부정 대조는 위조 origin/Host 직접 실행·다른 설치키·공개키 바꿔치기·등록 코드 replay·승인 범위 변경·nonce 동시 재생·철회 경합·UI 위장·정당 키의 서명 대리·실시간 relay·기밀 데이터 도청이다. 다른 확장이 정당 확장에 서명을 요청하며 사용자가 읽기 범위를 오인하는 사례, 등록 철회와 기존 결과 읽기가 경합하는 사례도 포함한다. relay 및 침해된 확장 상황은 단순히 모두 거부된다고 가정하지 않고, 각 허용 행위가 신뢰 모델·승인 범위에 미치는 영향을 기록한다. 환경·UI를 확인할 수 없으면 위험 기능은 보류한다. 모든 제품 실행 시험은 NOT RUN이다.

## 남은 사항

사용자는 등록키 기반 주체와 Desktop의 요청별 승인을 채택했다. 종단 기밀성·무결성·키 저장 실패 차단·부수 정보 완화 계약은 [종단 보안 채널 설계](../EXTENSION_SECURE_CHANNEL.md)와 [설치별 인증 설계](../CLIENT_INSTALLATION_AUTH_DESIGN.md)로 설계 확정했다. 원격 Host(SSH/WSL/Container) 확장 지원과 실제 OS·브라우저·IDE 배포 및 제품 보안 시험 실행은 제품 구현·검증 단계 과제로 남는다. 이 결정은 사용자에게 인증정보를 보내거나 새로운 계정을 요구하지 않는다.
